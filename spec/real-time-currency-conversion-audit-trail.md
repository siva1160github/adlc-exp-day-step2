**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**In Scope:**
- Backend conversion API in `src/backend`, added to `src/backend/OuterloopLabApi.sln`, targeting `net10.0`, with an endpoint that converts an amount from one currency to another using a live external rate.
- External provider client that reads its base URL exclusively from `CURRENCY_API_BASE_URL` (defaulting to `https://frankfurter.dev`), using `IHttpClientFactory`.
- Flexible JSON property mapping / abstraction layer so provider schema variations (`rates` vs `conversion_rates`) do not affect internal compliance tracking.
- Audit trail persistence in Cosmos DB on every conversion: server-generated execution timestamp (UTC, sub-second precision) plus any date/sequence markers returned by the provider.
- Audit retrieval endpoint that returns any past conversion (amount, rate, provider date, server timestamp) for auditor reconstruction.
- Startup provisioning in `Program.cs`: best-effort ARM control-plane attempt, then mandatory token-authenticated data-plane `CreateDatabaseIfNotExistsAsync`/`CreateContainerIfNotExistsAsync`; startup fails if the data-plane step fails.
- Frontend in `src/frontend` (Vite/React, Node 24.*) that calls the backend via runtime `VITE_API_URL`, with the `__VITE_API_URL__` placeholder replacement performed by a generic entrypoint script.
- Unit/integration tests for conversion math, tolerant mapping, and audit record shape, run via `src/backend/OuterloopLabApi.sln`; CI uses `dotnet-version: 10.0.x`.

**Out of Scope:**

- End-user authentication, authorization, or per-user RBAC inside the application.
- Currency settlement or payment execution — conversion and audit only, no movement of funds.

**Feature Constraints:**
- Use `IHttpClientFactory` with a typed client for every call to the external currency provider; never `new HttpClient()` directly.
- Provider response mapping must be tolerant: parse via `JsonDocument`/a normalization abstraction that reads whichever key is present (`rates` or `conversion_rates`) and ignores unknown fields; do not bind to a hardcoded third-party response class.
- Every audit record must store both `ServerTimestampUtc` (server-generated, e.g. `DateTimeOffset.UtcNow`, kept at sub-second precision) and `ProviderTimestamp`/`ProviderDate` (whatever the provider returned, even if it is only a calendar date). Both must be returned by the audit retrieval endpoint.
- External HTTP failures (e.g. `HttpRequestException`, `TaskCanceledException` timeout, `JsonException`) must be caught and translated into a domain-level result/exception; the API must return a `ProblemDetails` response with status 503 when the upstream rate provider fails — never leak raw network or serialization error details.
- Configuration must be mapped/bound directly from environment variables using the exact keys in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` (e.g. `AZURE_MANAGED_IDENTITY_CLIENT_ID`); no local settings configuration files as fallbacks.
- Cosmos DB data access must use `Microsoft.Azure.Cosmos` with `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`; zero connection strings, master keys, or account keys anywhere in code, configuration, or logs.
- Startup ordering in `Program.cs`: (1) best-effort ARM provisioning with `Azure.ResourceManager`/`Azure.ResourceManager.CosmosDB`; (2) token-authenticated data-plane `CreateDatabaseIfNotExistsAsync`/`CreateContainerIfNotExistsAsync`; (3) proceed only if database/container are available, otherwise fail startup.
- Frontend must never compile `VITE_API_URL` into the bundle; the built `index.html` must keep the `__VITE_API_URL__` placeholder so the generic entrypoint script can substitute it at container runtime.
- An optional short-TTL in-memory rate cache is permitted, but it must never change the rate persisted to the audit trail — the exact rate used for the conversion must always be stored on the audit record.
- All `dotnet` build/test commands must target `src/backend/OuterloopLabApi.sln`; CI must pin `dotnet-version: 10.0.x` and the backend project must target `net10.0`.

**Expected Outcome:**
- Sample conversion. Request: `GET /api/currency/convert?from=USD&to=EUR&amount=100.00` with provider response `{"date":"2026-08-01","base":"USD","rates":{"EUR":0.92}}` returns HTTP 200 with:
  ```json
  {
    "from": "USD",
    "to": "EUR",
    "amount": 100.00,
    "convertedAmount": 92.00,
    "rate": 0.92,
    "providerDate": "2026-08-01",
    "serverTimestamp": "2026-08-01T09:15:30.1234567Z"
  }
  ```
  and persists an audit record containing both `serverTimestamp` (sub-second) and `providerDate`.
- Tolerant mapping: with `CURRENCY_API_BASE_URL` pointed at a provider that returns `conversion_rates` instead of `rates` (e.g. `{"conversion_rates":{"EUR":0.92}}`), the same request returns the identical response shape above — proving the abstraction layer.
- Failure handling: with `CURRENCY_API_BASE_URL` pointed at an unreachable endpoint, the same request returns a `ProblemDetails` response with status 503 and no raw exception content; the app remains healthy.
- Audit reconstruction: `GET /api/currency/audit/{id}` returns the stored conversion including both timestamps, so an auditor can reconstruct any past conversion on demand.
- Build/test: `dotnet build src/backend/OuterloopLabApi.sln` succeeds on `net10.0` and `dotnet test src/backend/OuterloopLabApi.sln` passes.
- Frontend runtime URL: the container starts with `VITE_API_URL` set at runtime; the served built `index.html` contains no hardcoded API URL and shows `__VITE_API_URL__` replaced by the runtime value.
